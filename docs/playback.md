# Воспроизведение на станции: как это устроено и на чём спотыкались

Короткий разбор внутреннего механизма — тот минимум, который нужен, чтобы не повторять наших ошибок при доработке плеера.

## Схема

1. `zvukd` скачивает трек из «Звука» в `/data/local/tmp/zvukd/`.
2. Он же поднимает HTTP-раздатчик на `0.0.0.0:8765` и выдаёт станции ссылку
   `http://127.0.0.1:8765/<файл>?t=<метка>`.
3. Ссылка уходит штатному плееру командой Glagol `externalCommandBypass` → `audio_play`
   (protobuf: поле 1 = имя команды, поле 2 = JSON `{"stream":{"url","format","type","offset_ms"},"set_pause":false}`).
4. Файл забирает **родной плеер станции** (`maind --mediad`), поэтому Алиса продолжает
   отвечать, а громкость, пауза и мультирум остаются штатными. Борьбы за ALSA нет.

## Обязательное условие: поддержка Range

Раздатчик **обязан** отвечать на `Range: bytes=<start>-` кодом `206` с честными
`Content-Range` и `Content-Length`, а в `HEAD`/`200` отдавать `Accept-Ranges: bytes`.

Без этого станция не может начать трек с середины: она молча откатывается на нулевую
секунду. Симптом ровно такой: пауза держит позицию (например, 10 с), а «продолжить»
начинает с начала. Позиция в статусе при этом растёт нормально, и по ней проблему
не видно — поэтому проверять надо именно переход «пауза → продолжение».

## Почему «продолжить» — это снова `audio_play`, а не `play`

Команда `play` возобновляет **прошлую сущность станции** — то, что она играла до нас
(в нашем случае «32 радио», поток `strm-*.strm.yandex.net`). Поэтому продолжение
делается повторным `audio_play` того же файла с `offset_ms`, равным позиции паузы.

## Как убедиться, что играет именно наш файл

Ответ станции на команду (`status: SUCCESS`) ничего не доказывает — это статус конверта.
Единственный надёжный источник — её собственный лог:

```sh
grep -a "8765" /data/quasar/daemons_logs/mediad.log* | tail -3
```

Там видно `AudioClient created … uri=http://127.0.0.1:8765/…` и строку
`play, state=IDLE|PAUSED, url=http://127.0.0.1:8765/…`. Появление `strm.yandex.net`
означает, что станция ушла на свой поток, а не на наш файл.

## Две ловушки при запуске демона

- **Два экземпляра дерутся за сокет.** Тогда `play` попадает одному, а `status` читает
  другой: «сыграло, но статус пустой». Демон при старте убивает чужие копии — не
  запускайте второй вручную «для проверки».
- **Запуск из SSH-сессии без отвязки.** Демон, поднятый обычным `&` или через
  `start-stop-daemon -b`, умирает вместе с сессией. Рабочий вариант — `setsid` плюс
  фоновый запуск (`/data/local/bin/zvukd-start.sh`), либо перезагрузка: автозапуск
  `S97station-root` поднимает плеер из init-контекста.

## Пауза, конец трека, очередь

- **Пауза должна замораживать позицию.** Если считать её по времени с начала
  воспроизведения, за время паузы счётчик «убегает», и продолжение прыгает вперёд
  ровно на длительность паузы (пауза 12 с — трек уехал на 12 с). Позиция паузы
  запоминается отдельно и сбрасывается при продолжении.
- **Конец трека — по позиции станции, а не по отданным байтам.** Станция скачивает
  файл за секунды, поэтому «байты перестали расти» наступает почти сразу: движок
  считал трек законченным и переключал очередь через ~10 с после старта. Признак
  конца — `позиция + 1,5 с >= длительности`, и только когда не пауза.
- Проверено: The Rover доиграл 205 с из 217 и сам перешёл на следующий трек; на
  34-й секунде переключения нет.

## Почему голосовые «продолжи»/«дальше» нельзя ставить сразу

На эти слова её облако отвечает **позже нашей локальной команды** и включает свой
поток поверх нашего файла: слушатель срабатывает за доли секунды, а она — через
1–3 с. Поэтому локальная команда для `resume`/`next` выжидает ~3 с, и уже потом
забирает звук (`stop` + наш `audio_play` с нужной секунды).

Дополнительно плеер замечает подмену по названию трека, которое сообщает станция
(чужое имя вместо нашего) и возвращает наш файл с текущей секунды — не чаще раза
в 4 с, чтобы не бороться с ней бесконечно.
